# 毕业设计开发与部署计划

执行顺序：**最小基线与本地 Linux 部署 → WebRTC 双端原型与迁移 → 既有功能回归 → 共享会议记录 → 个人文字 Agent 与纪要 → 本地验收 → 云端部署**。

应用场景为小规模课题组例行组会，范围见 [首模块计划](./毕业设计首模块计划.md)，其他候选模块见 [长期规划](./长期愿景与模块规划.md)。本计划优先于历史 S/A 阶段顺序；AI 语音播报不在本阶段范围内。

## 1. 当前起点

- 已有代码：Qt 会议客户端、Go 信令、MySQL 建表、Python 文字助手、人像分割与 YOLO；RNNoise 改动尚未独立提交。运行环境长期未联调，需重新验证。
- 数据库已确认只有 `users`、`meeting_events`；聊天原文历史、ASR 转写、会议上下文工具与纪要均未实现，事件归档不能替代聊天或发言原文。
- Go 源码与服务模板在仓库内；ZLMediaKit 源码在仓库外的 `D:\lib\ZLMediaKit`，部署时需归档版本、配置与启动方式。
- 旧云实例状态待控制台确认；未找到云端 MySQL 导出备份。本地旧 SQLite 只作为可选数据来源，不等同云端备份。
- 当前 Qt 客户端依赖 Windows 采集与库路径，本轮先保持 Windows 运行。已定位本机 VMware Ubuntu 虚拟机（2 vCPU、4 GiB、NAT），尚需开机确认系统版本、地址与 SSH；未完成 Linux 服务恢复。
- 当前代码仍使用 RTMP；目标调整为 WebRTC + SFU，迁移排在共享记录与个人 Agent 开发之前。RTMP 暂留作对照与回退，不能将规划标成已实现。

## 2. 部署布局

| 组件 | 本地开发测试 | 后续云端 |
|---|---|---|
| Qt 客户端 | Windows，会议界面与个人助手窗口 | 仍在用户电脑运行 |
| Go 业务服务 | Linux，统一 TCP 9001；认证、会控、记录与查询 | 迁入云服务器 |
| WebRTC 媒体服务 | Linux，先验证自托管 SFU 与可达的 UDP 媒体链路 | 迁入云服务器，配置公网 ICE 候选和 TURN 回退 |
| ZLMediaKit/RTMP | 保留旧链路对照；也可评估其 WebRTC 接口 | 后续直播或协议转换按需部署 |
| MySQL | Linux，保存共享会议记录、私有问答与纪要 | 与服务同机，验证备份恢复 |
| Python 共享转写/Agent 服务（新增） | 可先运行在开发电脑，按会议订阅音轨、调用 ASR/LLM | 按资源保留本地或独立部署 |
| 现有视觉推理服务 | 保留本地分割、检测，按需加载 | 不要求与共享服务同机 |

首轮使用已定位的 VMware Ubuntu 虚拟机，服务交给 systemd 托管；开机后记录实际版本、架构、地址、可用资源及 Windows 到虚拟机的连通性。

个人助手是私有的交互入口，后台服务可供多人共享；无需每个客户端各运行一套会议记录器。转写工作进程独立于个人入会和离会，直到主持人停止转写或会议结束。共享服务须能访问媒体和业务接口，不能依赖仅当前电脑可达的 `127.0.0.1`。

模型按需加载，LLM 复用已有 API 并限制用量。ASR 先评测样本的延迟、内存和中文效果，再选择现成模型或接口，不预设需要 GPU。

## 3. WebRTC 选型与迁移边界

采用服务器转发的多人拓扑（SFU），各客户端向服务器发布媒体并订阅其他成员，避免全互连。优先走 UDP；受限网络通过 ICE/TURN 及可用的 TCP/TLS 路径回退。相关机制见 [WebRTC 传输标准](https://www.rfc-editor.org/rfc/rfc8835.html)。

| 路线 | 用途与约束 |
|---|---|
| 首选验证：LiveKit 自托管 + 原生 C++ SDK | 验证 Windows/MSVC、外部视频/PCM、Qt 兼容性及 Python 分用户音轨读取。[官方 SDK](https://docs.livekit.io/reference/client-sdk-cpp/) |
| 备选：ZLMediaKit WebRTC + 配套原生客户端 | 验证客户端 SDK、音频播放与共享记录器接入；不假定能直接使用 LiveKit SDK。[官方接口](https://docs.zlmediakit.com/guide/protocol/webrtc/webrtc_signaling_interaction_format.html) |

SDK 与媒体服务器必须配套验证；首选原型通过后才固定版本。工程中残留的 MixedReality-WebRTC 已归档，不作为新主链依赖。[官方仓库状态](https://github.com/microsoft/MixedReality-WebRTC)

- Go 继续负责账号、业务房间、会控、聊天、白板与存储；接入 SFU 时增加受限入房凭证及身份映射。SDK 自带的媒体协商不重复塞进业务信令。
- 迁移必须覆盖发布和订阅两端。Qt 将预处理后的视频帧、PCM 交给 RTC 适配层；SDK 负责实时编码、传输与播放节奏，FFmpeg 保留本地录制等用途。
- 音频目标优先 Opus/48kHz，适配当前 44.1kHz 输入；视频验证 H.264/VP8 协商。自采集音频需验证回声参考接入，避免 RNNoise 与 SDK 降噪盲目叠加。
- 接收音轨应能独立送给 ASR、录制和播放；实际轨道状态需与会控同步。旧 AAC/FLV 编码包不能直接作为完整 RTC 接入方案。

## 4. 共享记录与个人助手约定

- **会议身份**：每次会议创建独立会话 ID，房间号可复用。后端核验登录身份与会议权限，不信任请求里自行填写的用户名或房间号。
- **公开历史**：Go 将聊天先持久化再广播；主持人显式开启转写，成员能看见状态。Python 经受控接口提交转写，由 Go 校验与持久化。每条正式记录带会话、成员、时间和序号；按成员授权允许补读本场此前的公开记录。
- **迟到与重连**：历史查询配合服务器游标和增量订阅，按记录 ID/序号去重补取，覆盖查询期间的新消息。转写开启前或服务中断造成的缺口明确标记，不生成虚构记录。
- **个人问答**：按用户、会议和对话线程隔离存储与上下文；不进入会议聊天广播，也不混入公开纪要。LLM 按提问或摘要请求调用，不持续处理每一帧音频。
- **受控工具**：先提供会议记录查询、上下文摘要和纪要草稿保存。模型选择工具，程序校验参数与权限，展示执行中、成功、失败或取消；禁止模型任意执行 SQL 或越权查询。
- **输出可信度**：回答关联发言和时间；模型建议与讨论结论分开。纪要可编辑保存导出，负责人、期限或决策未明确时标记待确认。首版使用关系库查询，不以向量库或多 Agent 为前置条件。

## 5. 分阶段执行

| 阶段 | 主要工作 | 通过条件 |
|---|---|---|
| D0 环境与最小基线 | 确认 Ubuntu、SSH、Windows 构建及 RTC SDK 依赖；保存 RTMP 对照配置 | 基线可运行，地址、资源与回退入口明确 |
| D1 本地服务恢复 | 安装 MySQL、业务账号与 Go；部署候选 WebRTC 服务；记录版本、配置和启动方式 | 业务登录与写库可用；候选服务可连接并协商媒体 |
| D2 WebRTC 原型与迁移 | 先做 Windows 原生双端原型，再抽取媒体会话接口，接入发布/订阅、共享、录制及音效 | 双端连续会议 30 分钟；弱网及断网恢复可测，功能不再依赖 RTMP 中间链路 |
| D3 首页与完整回归 | 简单首页，回归会控、聊天、白板、美颜、虚拟背景、YOLO、降噪和原有助手 | 退出不残留线程；状态与实际轨道一致，录制及共享可用；RNNoise 单独复测 |
| D4 共享记录与转写 | 持久化聊天、分成员 ASR、历史查询和游标补取 | 迟到/重连补读历史；个别成员离线不影响记录，缺口有标记 |
| D5 个人 Agent 与纪要 | 复用独立助手窗口，接入工具调用、阶段摘要与纪要编辑导出 | 两名成员可分别提问且互不可见；回答关联记录，未决事项不编造 |
| D6 本地联合验收 | 完整演示、失败恢复、持久化、打包和备份恢复测试 | AI 不可用时会议继续；双房间及私有问答隔离，重启后记录可读 |
| D7 云端复现 | 迁移相同版本与数据，配置媒体可达地址、UDP 端口、TLS 与 TURN，再做异地双端回归 | 公网媒体、受限网络回退、历史补取及备份恢复通过 |

每阶段完成「开发 → 测试 → 记录结果」后再推进，不预先将未测试功能标记完成。

D2 内按「原生 SDK 构建与原始帧回调 → 双端音视频 → 自采集视频/PCM → 主工程适配 → 全功能回归」推进。先分别验证上下行都是 WebRTC；只把 RTMP 拉流换成 WebRTC 不算迁移完成。

弱网测试逐项加入带宽限制、丢包、抖动和短时断网；记录 RTT、丢包率、码率、冻结、音画偏差和恢复耗时，与同条件 RTMP 对照。WebRTC 不替代对 CPU 过载、采集阻塞和编码积压的定位。

16 周安排供进度检查：1–2 周环境与最小基线；3–6 周 RTC 原型、迁移及回归；7–10 周记录、转写与个人 Agent；11–12 周纪要与联合验收；13–16 周云端复现、文档和演示。写作与翻译并行开展。第 4 周检查 RTC 技术风险并调整范围。

## 6. 关键约定

- **配置**：明确客户端实际读取的 ini 路径；本地与云端分别保存地址。WSL 同机、虚拟机与局域网用各自可达地址，不统一写成 `127.0.0.1`。Go 示例默认端口与当前代码默认值需在 D1 对齐。
- **网络**：业务 WebSocket 与媒体连接分别检测；API 能连不代表 UDP 可达。媒体地址、端口和 TURN 配置按最终服务固定，不能沿用仅放行 1935/9001 的旧部署方式。
- **音频**：共享记录器订阅全部已授权参会者的独立音轨，与客户端焦点播放静音分离；身份来自已认证会话。参考 [原始音轨接口](https://docs.livekit.io/transport/media/raw-tracks/)。本阶段不接 TTS、主动发言或停止播报。
- **数据**：新增共享记录、私有问答、纪要与工具执行记录；使用可追溯迁移脚本，记录会话与访问范围。
- **部署资产**：版本清单、无密钥配置示例、Go/ZLM 服务模板、建库与备份恢复步骤入仓；真实凭据和数据单独保存。

WebRTC 是本轮优先迁移项；S6/OpenGL、直播导播与完整模块市场仍后置。原型阶段若遇 SDK 或资源瓶颈，先记录并调整实现路线，再进入 AI 新功能。

## 7. 云端迁移与最终交付

迁移前备份本地数据库与配置，在新环境验证恢复；最终切换采用短暂停写后导出，避免遗漏期间新增数据。公网仅开放实际使用的服务入口，MySQL 继续走服务器本机连接；AI 和管理接口不直接裸露公网。迁移完成前保留可运行的本地环境。

最终交付：WebRTC 会议客户端、Linux 部署包、接口与使用文档、数据库恢复步骤、弱网对照与演示记录。正式材料要求见 [首模块计划](./毕业设计首模块计划.md#4-预期成果)。

**下一步继续 D0：启动已有 Ubuntu 虚拟机，确认系统、IP、内存与 SSH，再执行 D1。当前文档更新不代表已部署服务或实现上述新增能力。**
