# 毕业设计开发与部署计划

执行顺序：**恢复最小基线 → 本地 Linux 部署 → WebRTC 双端原型与迁移 → 毕设新增能力 → 本地验收 → 云端部署**。

功能范围见 [毕业设计首模块计划](./毕业设计首模块计划.md)，其他候选模块见 [长期规划](./长期愿景与模块规划.md)。本计划优先于历史 S/A 阶段顺序；当前尚未开始本地部署。

## 1. 当前起点

- 已有代码：Qt 会议客户端、Go 信令、MySQL 建表、Python AI 助手、人像分割、YOLO 与 RNNoise。长期未联调，需重新验证。
- Go 源码与服务模板在仓库内；ZLMediaKit 源码在仓库外的 `D:\lib\ZLMediaKit`，部署时需归档版本、配置与启动方式。
- 旧云实例状态待控制台确认；未找到云端 MySQL 导出备份。本地旧 SQLite 只作为可选数据来源，不等同云端备份。
- 当前 Qt 客户端依赖 Windows 采集与库路径，本轮先保持 Windows 运行。
- 当前代码仍使用 RTMP；目标调整为 WebRTC + SFU，迁移排在会议机器人开发之前。RTMP 暂留作对照与回退，不能将规划标成已实现。

## 2. 部署布局

| 组件 | 本地开发测试 | 后续云端 |
|---|---|---|
| Qt 客户端 | Windows | 仍在用户电脑运行 |
| Go 信令 | Linux，统一使用 TCP 9001 | 迁入云服务器 |
| WebRTC 媒体服务 | Linux，先验证自托管 SFU 与可达的 UDP 媒体链路 | 迁入云服务器，配置公网 ICE 候选和 TURN 回退 |
| ZLMediaKit/RTMP | 保留旧链路对照；也可评估其 WebRTC 接口 | 后续直播或协议转换按需部署 |
| MySQL | Linux，本机连接 | 与服务同机，保留数据备份 |
| Python AI | 起步保留在开发电脑 | 视资源保留本地或独立部署 |

首轮采用 Linux 服务与 systemd 托管。先确认 Linux 是 WSL2、虚拟机、双系统还是另一台电脑，记录版本、架构、地址和可用资源；双系统不能与同机 Windows 客户端同时运行。

AI 模型按需加载，LLM 复用 API 并记录用量。个人助手仍是客户端私有服务；共享会议机器人另设一个会话实例，地址和权限单独配置。

## 3. WebRTC 选型与迁移边界

采用服务器转发的多人拓扑（SFU），各客户端向服务器发布媒体并订阅其他成员，避免全互连。优先走 UDP；受限网络通过 ICE/TURN 及可用的 TCP/TLS 路径回退。相关机制见 [WebRTC 传输标准](https://www.rfc-editor.org/rfc/rfc8835.html)。

| 路线 | 用途与约束 |
|---|---|
| 首选验证：LiveKit 自托管 + 原生 C++ SDK | 有原生 C++ 与 Python 接入路线，适合后续机器人订阅音轨；须先验证 Windows/MSVC、原始帧接入及现有 Qt 工程兼容性。[官方 SDK](https://docs.livekit.io/reference/client-sdk-cpp/) |
| 备选：ZLMediaKit WebRTC + 配套原生客户端 | 复用现有媒体服务器；需验证客户端 SDK、音频播放与 Python 机器人接入。[官方接口](https://docs.zlmediakit.com/guide/protocol/webrtc/webrtc_signaling_interaction_format.html) |

SDK 与媒体服务器必须配套验证；首选原型通过后才固定版本。工程中残留的 MixedReality-WebRTC 已归档，不作为新主链依赖。[官方仓库状态](https://github.com/microsoft/MixedReality-WebRTC)

- Go 继续负责账号、业务房间、会控、聊天、白板与存储；接入 SFU 时增加受限入房凭证及身份映射。SDK 自带的媒体协商不重复塞进业务信令。
- 迁移必须覆盖发布和订阅两端。Qt 将预处理后的视频帧、PCM 交给 RTC 适配层；SDK 负责实时编码、传输与播放节奏，FFmpeg 保留本地录制等用途。
- 音频目标优先 Opus/48kHz，适配当前 44.1kHz 输入；视频验证 H.264/VP8 协商。自采集音频需验证回声参考接入，避免 RNNoise 与 SDK 降噪盲目叠加。
- 接收音轨应能独立送给 ASR、录制和播放；实际轨道状态需与会控同步。旧 AAC/FLV 编码包不能直接作为完整 RTC 接入方案。

## 4. 分阶段执行

| 阶段 | 主要工作 | 通过条件 |
|---|---|---|
| D0 环境与最小基线 | 确认 Linux 形态、Windows 构建及 RTC SDK 依赖；保存 RTMP 对照配置 | 现有客户端可构建，网络方案与回退入口明确 |
| D1 本地服务恢复 | 安装 MySQL、业务账号与 Go；部署候选 WebRTC 服务；记录版本、配置和启动方式 | 业务登录与写库可用；候选服务可连接并协商媒体 |
| D2 WebRTC 原型与迁移 | 先做 Windows 原生双端原型，再抽取媒体会话接口，接入发布/订阅、共享、录制及音效 | 双端连续会议 30 分钟；弱网及断网恢复可测，功能不再依赖 RTMP 中间链路 |
| D3 首页与完整回归 | 加入首页与内置会议入口，验证会控、聊天、白板、美颜、虚拟背景、YOLO、降噪和 AI 助手 | 退出不残留线程；实际静音/关摄像头与成员状态一致，录制及共享可用 |
| D4 转写与 Agent | 先验证 ASR 样本，再接入分用户音轨；增加上下文检索、纪要保存工具与执行状态 | 两名成员可区分归属；工具调用可追踪，纪要可编辑导出 |
| D5 机器人语音参会 | 主持人启用机器人；结合会议记录回答，TTS 注入独立媒体源，支持停止播报 | 全员听见且不受焦点切换影响；机器人不会因自己的声音循环触发 |
| D6 本地联合验收 | 完整演示、失败恢复、持久化、打包和备份恢复测试 | AI 不可用时会议继续；双房间数据隔离，重启后资料可读 |
| D7 云端复现 | 迁移相同版本与数据，配置媒体可达地址、UDP 端口、TLS 与 TURN，再做异地双端回归 | 公网媒体、受限网络回退与重连可用；机器人、备份及恢复通过 |

每阶段完成「开发 → 测试 → 记录结果」后再推进，不预先将未测试功能标记完成。

D2 内按「原生 SDK 构建与原始帧回调 → 双端音视频 → 自采集视频/PCM → 主工程适配 → 全功能回归」推进。先分别验证上下行都是 WebRTC；只把 RTMP 拉流换成 WebRTC 不算迁移完成。

弱网测试逐项加入带宽限制、丢包、抖动和短时断网；记录 RTT、丢包率、码率、冻结、音画偏差和恢复耗时，与同条件 RTMP 对照。WebRTC 不替代对 CPU 过载、采集阻塞和编码积压的定位。

## 5. 关键约定

- **配置**：明确客户端实际读取的 ini 路径；本地与云端分别保存地址。WSL 同机、虚拟机与局域网用各自可达地址，不统一写成 `127.0.0.1`。Go 示例默认端口与当前代码默认值需在 D1 对齐。
- **网络**：业务 WebSocket 与媒体连接分别检测；API 能连不代表 UDP 可达。媒体地址、端口和 TURN 配置按最终服务固定，不能沿用仅放行 1935/9001 的旧部署方式。
- **音频**：转写接入全部已授权参会者音轨，与焦点播放静音分离；身份来自已认证会话。先按钮/文本点名，再接语音提问和结束判断。
- **Agent**：工具参数、权限与执行结果由程序校验；私人问答不广播，会议机器人回答按房间同步；纪要中不明确的负责人和期限标为待确认。
- **数据**：先支持转写、纪要与执行记录持久化；新增表使用可追溯迁移脚本，记录会话和访问范围。
- **部署资产**：版本清单、无密钥配置示例、Go/ZLM 服务模板、建库与备份恢复步骤入仓；真实凭据和数据单独保存。

WebRTC 是本轮优先迁移项；S6/OpenGL、直播导播与完整模块市场仍后置。原型阶段若遇 SDK 或资源瓶颈，先记录并调整实现路线，再进入 AI 新功能。

## 6. 云端迁移与最终交付

迁移前备份本地数据库与配置，在新环境验证恢复；最终切换采用短暂停写后导出，避免遗漏期间新增数据。公网仅开放实际使用的服务入口，MySQL 继续走服务器本机连接；AI 和管理接口不直接裸露公网。迁移完成前保留可运行的本地环境。

最终交付：WebRTC 会议客户端、Linux 部署包、版本与配置示例、数据库恢复步骤、弱网对照测试、演示流程与毕设论文材料。
