# A2 AI 虚拟背景开发顺序

## 1. 目标

A2 的目标不是“接一个模型试试看”，而是把 `AI 虚拟背景` 做成一个：
- 可实时使用
- 不明显拖垮本地会议主链
- 可演示
- 可在面试中讲清楚工程设计

第一阶段只覆盖：
- 本地摄像头
- 本地预览
- 本地推流

第一阶段不覆盖：
- 远端画面
- 屏幕共享
- OpenGL 叠加
- GPU 推理优化

---

## 2. 技术路线选择

### 2.1 MediaPipe Selfie Segmentation

优点：
- 上手快
- 已经针对自拍/人像背景分割做过优化
- 第一版更容易快速出效果
- CPU 下也比较容易跑起来

缺点：
- 工程可控性一般
- 模型和推理链抽象不如 ONNX 通用
- 对后续“简历写法”和“迁移到别的模型”帮助没那么强

适合：
- 想最快做出可演示版本
- 更重视短期出效果

### 2.2 ONNX Runtime + 现成人像分割模型

优点：
- 更贴近很多招聘里提到的 `ONNX / ONNX Runtime`
- 推理框架更通用，后面换模型更顺
- 后续如果从 Python 挪到 C++，技术路线更自然
- 更适合继续往 `A5` 和后续性能优化演进

缺点：
- 第一版集成工作量更大
- 需要自己处理：
  - 输入预处理
  - 输出后处理
  - mask 缩放与融合
  - 超时与缓存

适合：
- 既要做功能，也要兼顾简历和面试表达
- 希望后续演进空间更大

### 2.3 当前项目建议

当前项目的 A2 推荐路线是：

`ONNX Runtime + 现成人像分割模型`

原因：
- 你已经明确提到招聘里经常出现 `onnx`
- 这个项目后面还有 `S6 / A5`
- 现在直接走 ONNX 路线，更利于后面讲“推理层”和“渲染层”的分工

如果中途发现 ONNX 第一版落地成本明显过高，再退一步用 MediaPipe 做 PoC，也可以接受；但当前默认规划仍以 ONNX 路线为准。

---

## 3. A2 与 S6 / A5 的关系

这里必须记清楚：

- `A2`：AI 虚拟背景
- `S6`：OpenGL 渲染层升级
- `A5`：AI + OpenGL 结果叠加

关系是：
- `A2` 可以先于 `S6`
- `S6` 不等于 `A2`
- `A5` 依赖 `S6`

当前推荐顺序：
1. 先做一次轻量基线盘点
2. 进入 `A2`
3. A2 稳定后，再决定是否进入 `S6`
4. `A5` 放在 `S6` 后面

---

## 4. 开发范围控制

A2 第一版只做三种效果：
- 背景虚化
- 纯色背景
- 图片背景

第一刀只先交付：
- 背景虚化

原因：
- 风险最低
- 最容易先判断分割质量和主链压力
- 背景虚化不依赖额外素材管理

---

## 5. 实施顺序

### 阶段 A2-P0：轻量基线盘点

先记录当前无虚拟背景时的：
- 单人会议 CPU/内存
- 双人会议 CPU/内存
- 开美颜时 CPU/卡顿情况
- 屏幕共享切换前后表现

目的：
- 给 A2 引入后的性能变化留基准
- 避免后面分不清是旧问题还是新问题

退出标准：
- 拿到至少一组“未开启虚拟背景”的稳定基线数据

### 阶段 A2-P1：Python 侧分割接口

在 `pythonAiService` 新增：
- `POST /segment`

输入：
- 压缩后的本地摄像头帧

输出：
- 人像 mask
- 结果尺寸信息
- 推理耗时

第一版要求：
- 只返回单张 mask
- 不做流式
- 不做多模型切换

退出标准：
- Python 单独测试时能稳定返回可用 mask

### 阶段 A2-P2：客户端分割调用层

Qt 侧新增一个很薄的调用层，例如：
- `AiSegmentationClient`

职责：
- 向 `/segment` 发请求
- 接收 mask
- 做超时控制
- 丢弃过期结果

这一层不直接改业务逻辑，只做“异步请求 + 结果回调”。

退出标准：
- 本地可单独测通“发图 -> 收 mask”
- Python 慢或挂掉时，客户端不会卡死

### 阶段 A2-P3：接入 VideoCapture，先做背景虚化

接入点：
- `videocapture.cpp` 的 `captureLoop()`

顺序：
1. 摄像头抓原始帧
2. 每隔几帧发一张缩小图去做分割
3. 缓存最近一张 mask
4. 主链继续跑，不等推理结果
5. 对当前帧使用最近 mask 做背景虚化
6. 再送去本地预览与推流

这里必须做：
- 限频
- 超时
- 结果缓存
- 降级

退出标准：
- 开启背景虚化后，本地预览可见明显效果
- 会议仍可正常推流
- 没有明显 UI 卡死

### 阶段 A2-P4：纯色背景

在 P3 稳定后，再增加：
- 白色/灰色/品牌色等纯色背景

退出标准：
- 背景可稳定替换为纯色
- 边缘没有明显大面积闪烁

### 阶段 A2-P5：图片背景

在纯色背景稳定后，再加：
- 选择本地图片
- 作为背景融合

退出标准：
- 支持选择图片并稳定生效
- 错误图片路径或大图不导致崩溃

### 阶段 A2-P6：收口与回归

重点回归：
- 开关虚拟背景
- 切换美颜
- 切换共享
- 录制
- 双实例会议

退出标准：
- 主链没有明显回归
- 用户可稳定切换虚拟背景模式

---

## 6. 关键工程约束

A2 第一版必须遵守：

- 不能每帧都请求 AI
- 不能阻塞 UI 线程
- 不能阻塞采集热路径
- 不能在共享模式下强行继续做虚拟背景
- 不能为了效果牺牲到会议主功能不可用

推荐策略：
- 每 `3~5` 帧请求一次分割
- 推理输入最长边先压缩到 `256~512`
- 分割超时就直接丢弃，沿用旧 mask
- 共享开启时自动关闭虚拟背景

---

## 7. 与现有美颜的配合

当前建议：
- 允许虚拟背景和轻量美颜共存
- 第一版不追求“强美颜 + 强分割”同时最优

推荐顺序：
1. 取摄像头帧
2. 美颜
3. 使用最近 mask 做背景处理
4. 输出到预览与推流

后面如果发现 CPU 压力明显增加，再考虑增加互斥策略或自动降档。

---

## 8. 当前明确不做

A2 第一版不做：
- 发丝级精细抠图
- 多人同帧复杂分割
- 远端视频背景替换
- 共享画面背景替换
- GPU 推理
- OpenGL 叠加
- YOLO 联动
- 自动构图

---

## 9. 面试可讲述点

A2 做完后，面试里重点讲：
- Qt/C++ 负责会议主链
- Python 服务负责 AI 推理
- 两者通过 HTTP(JSON) 异步通信
- 通过限频、缓存、超时降级保证不拖垮视频主链
- 第一版实现了背景虚化、纯色背景、图片背景的分阶段落地

---

## 10. 当前结论

当前 A2 的实际执行顺序固定为：

1. 轻量基线盘点
2. Python `/segment`
3. Qt `AiSegmentationClient`
4. `VideoCapture` 接入
5. 先做背景虚化
6. 再做纯色背景
7. 再做图片背景
8. 最后回归收口

不要跳步，不要第一版就同时上：
- 分割
- 多种背景
- OpenGL
- YOLO
- GPU 优化
